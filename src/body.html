Model documentation — state-update rules & the cascade feedback loop

Fidelity commitment

The simulation encodes the specific mechanisms that produce memory-pressure cascades on real clusters, at one-second resolution. Memory is the only resource dimension. Everything you see — including any cascade — is produced by the update rules below acting on state; there is no timeline, no canned sequence, and the RNG is seeded (same seed ⇒ identical run).

State-update rules (one tick = 1 s, in this order)

  • 1. Pod working sets. Each running pod's usage follows a mean-reverting approach to a per-pod target: U += (T − U)/τ · s + ε, where ε ~ N(0, σ²) and s = 1 − 0.6·PSIfull is a reclaim-stall throttle. Targets are drawn per pod as a fraction of the limit (default 75% ± 20%, capped at 92%) — apps grow into the room their limit grants, not their request. Leaky pods additionally gain leakRate Mi/s forever. Terminating pods drain linearly over their grace period; backoff pods hold zero.
  • 2. cgroup v2 memory.max. Any container whose usage reaches its limit is OOM-killed in place (the pod object stays bound): usage → 0, CrashLoopBackOff delay 10 s·2ⁿ capped at 300 s, then restart and regrow.
  • 3. Kernel OOM (every tick — the kernel doesn't wait for kubelet). If a node's working set (Σ pod usage + system daemons) reaches physical capacity, the kernel kills the container with the highest oom_score = 1000·usage/capacity + oom_score_adj, using kubelet's real adj values: Guaranteed −997, BestEffort 1000, Burstable min(max(2, 1000 − 1000·request/capacity), 999). Kernel OOM kills restart in place, like rule 2.
  • 4. Kubelet eviction manager (every 10 s per node, staggered). Signal: memory.available = capacity − workingSet. If below the hard threshold: evict one pod immediately, no grace. If below the soft threshold continuously for the grace period: evict one pod with min(pod grace, eviction-max-pod-grace-period). Victim ranking is the real one: pods whose usage exceeds requests first (all BestEffort usage qualifies), then lower priority, then largest usage-over-request. Either signal sets the MemoryPressure condition ⇒ NoSchedule taint, held for the pressure-transition period after the signal clears. Eviction marks the pod Failed at once: the scheduler stops counting its requests even while memory drains — a real and consequential gap.
  • 5. Controller. Each evicted/drained pod's controller creates a replacement after a short informer delay. Restarts (rules 2–3) do not reschedule — that distinction is why leaks crashloop in place but evictions travel. Pod specs are immutable: changing request/limit sliders rolls the workload gradually (bounded replacements per tick), as a Deployment would.
  • 6. Scheduler. Filters on requests only against allocatable = capacity − reserved − evictionHard (the real allocatable formula — raising the hard threshold genuinely shrinks what the scheduler may book), excludes tainted nodes, then scores by MostAllocated (bin-pack) or LeastAllocated (spread). The scheduler never sees actual usage. Unschedulable pods retry with backoff and are shown as Pending.
  • 7. Telemetry. Node PSI is derived from proximity to exhaustion (reclaim-stall proxy); metrics and events append to the history that drives the charts.

The feedback loop that makes a cascade

With limits above requests and working sets that track limits, a bin-packed node hosts more demand than it has physical memory — the scheduler booked requests, the kernel serves usage. The loop: growth pushes a packed node's memory.available under a threshold → kubelet evicts (or, if growth outruns the 10 s housekeeping cadence, the kernel OOM-kills first) → the eviction frees requests in the scheduler's books and taints the node → the controller replaces the pod → the scheduler, blind to usage, bin-packs the replacement onto the most-committed untainted node — typically the next-most-loaded one → the replacement regrows toward the same target and tips that node → repeat. Taints concentrate refugees on ever-fewer nodes (accelerating the wave); when transition periods lapse, pods flood back and the wave can oscillate. The loop terminates only when the state makes it terminate: demand shed below capacity, pods parked Pending, or parameters that keep usage inside requests.

Prove the emergence to yourself

  • Relax limits: drag Limit : request to 1.00×. Pods become Guaranteed; usage can no longer exceed what the scheduler booked, so Σ working set ≤ Σ requests ≤ allocatable and no threshold can trip. As the rolling replacement completes, the cascade dies — kills stop, pressure clears.
  • Raise thresholds: push soft/hard eviction up (e.g. 1536/1024 Mi). Two real effects compound: allocatable shrinks (scheduler books less per node) and kubelet acts before the kernel — kernel OOMs collapse and the failure mode turns into orderly early eviction + Pending backlog.
  • Shrink demand: lower Mean working set to ~45%. Same overcommit ratio, but after a transient the evictions rebalance packing below the hazard density and the cluster goes quiet — the cascade is a property of the state, not of the code path.
  • Inject a leak: one Burstable pod with a generous limit drags its node into pressure; watch neighbors get evicted (they exceed requests; the leaker may crashloop in place) and the displaced load propagate.

The same engine (src/engine.js) runs headlessly: node src/verify.mjs asserts all four behaviors plus determinism across seeds. See MODEL.md for the full ground-truth-vs-model table.

Deliberate simplifications (and why they're safe here)

  • All pod memory is anonymous; page cache isn't modeled. Kubelet's memory.available already excludes reclaimable inactive_file, so this matches the signal's semantics while skipping the reclaim buffer that delays — but doesn't change — the dynamics.
  • PSI is a derived proximity-to-exhaustion proxy shown per node and used only to stall allocation; real kubelets don't act on PSI either (PSI-based eviction is still alpha).
  • One container per pod; CPU, pids, and disk eviction signals omitted; scheduler reduced to NodeResourcesFit + taints (no affinity/spread constraints); kernel OOM kills one victim per pass; --eviction-pressure-transition-period defaults to 60 s here (real default 300 s) so oscillations are watchable.
